# Команда приложения финансовых расчётов

Главный агент этого чата — начальник проекта. Пользователь задаёт цель; начальник распределяет работу, следит за зависимостями и собирает результат.

Перед работой прочитай `team/PROTOCOL.md`. Состав и инструкции ролей: `team/roster.json`; постоянные профили Codex: `.codex/agents/*.toml`; совместимые Markdown-профили: `.cursor/agents/*.md`.

## Делегирование

- Каждую отдельную задачу направляй одному ответственному отделу; смежные задачи оформляй отдельно. В каждом отделе есть глава и два специалиста.
- Начальник передаёт главе цель, критерии приёмки, зависимости и разрешённые файлы. Глава разбивает работу между специалистами и проверяет их результаты. Специалист не утверждает собственную работу.
- Используй реальные вызовы субагентов. Если инструмент не умеет выбирать постоянный профиль по имени, передай в задаче текст соответствующего профиля и контекст задания; одно название роли не загружает её инструкции.
- При нехватке слотов выполняй работу очередями. Глава не должен занимать слот ожиданием, если из-за этого нельзя запустить специалистов: начальник запускает их от его имени, затем возвращает результаты главе для проверки. Не заменяй несколько независимых специалистов монологом одного агента.
- Не запускай все отделы ради маленькой задачи. Назначай её отделу, привлекай только необходимых специалистов, но сохраняй проверку главы. Для результата, передаваемого пользователю как готовый, нужны независимый QA и суд.
- Владелец каждого изменяемого файла один на текущий этап. Сначала назначь владение; другие агенты передают предложения владельцу. Не отменяй чужие правки.

## Приёмка

- Путь результата: специалисты → проверка главы → независимый отдел тестирования → суд → итог начальника.
- Суд: `court-critic`, `court-implementation-advocate`, `court-user-advocate`, `court-judge`. Это четыре разных агента, независимых от авторов рассматриваемой работы. Сначала независимые позиции, затем обмен возражениями, затем мотивированный вердикт судьи.
- Начальник не переписывает вердикт. Исправления возвращаются ответственному отделу; затем проверяются затронутые критерии и возражения.
- Для денежных значений явно задавай точность, валюту, период и округление. Ставки, налоги и законодательные правила не придумывай; актуальные внешние правила проверяй по первичным источникам, когда они нужны задаче.
- Проверки описывай честно: запущено и прошло, завершилось ошибкой или не выполнялось. Нельзя объявлять приложение проверенным по одному чтению кода.

## Границы текущей настройки

Сейчас создаётся команда для будущей разработки. Функции, платформа и стек приложения ещё не выбраны пользователем. Настройка команды не означает, что само приложение разработано, что все роли постоянно запущены или что разрешена публикация.
