# APP-014: план расширения обработки банковских уведомлений

2026-11-04, Asia/Qyzylorda. Глава `/root/import_backend_lead`, backend-data-lead. Этап: план и чтение кода существующей 0.2.0/code2; не реализация и не приёмка новой версии. Единственный изменённый файл — этот отчёт.

## Прочитано и установлено

Прочитаны полные AGENTS.md, team/PROTOCOL.md, профили backend-data-lead/backend-engineer/data-engineer, APP-009-backend-diagnosis.md. Уточнены BankNotificationService, BankMessageParser, ParseSupport, ReceiptParser, SourceTokens и ветви ingest LedgerStore; прочитаны соответствующие существующие parser-тесты. Ни новые тесты, ни Android/ADB/UI, ни уведомления телефона не запускались/не читались.

- **P14-01, подтверждённое ограничение извлечения:** BankNotificationService.notificationText берёт title, затем bigText либо text. EXTRA_TEXT_LINES читается только при пустом выбранном body. Непустой короткий body может не содержать полей, которые есть в textLines. Это не доказательство формата конкретного банка пользователя. Group summary намеренно пропускается: оно может описывать несколько операций, и его нельзя превращать в одну запись.
- **P14-02, подтверждённая консервативность:** BankMessageParser удаляет помеченный остаток из суммы операции, но затем добавляет AMBIGUOUS_TOTAL даже при одном явно распознанном платеже и отдельном балансе. Текущий тест explicitBankPaymentAndBalanceAreDifferentAmounts именно этого требует. Простое удаление причины без отдельной грамматики меняет ранее принятый контракт.
- **P14-03, подтверждённое ограничение валюты:** ParseSupport понимает KZT/₸, а тг/тенге/теңге нормализуются только в ReceiptParser. Уведомление с такими словами может потерять сумму и валюту. Предлагаемое bank-only правило нормализует точные отдельные слова, без изменения общих OCR-правил и без вывода валюты из настройки пользователя.
- **P14-04, подтверждённое ограничение направления:** ParseSupport.requiresReview блокирует любой перевод/transfer; BankMessageParser не распознаёт «Вы перевели/переведено/Вам перевели» как самостоятельные направления. Даже полный текст перевода попадает на проверку, часть полей может не заполняться. Само слово «перевод» не устанавливает направление, окончательность или перевод между своими счетами.
- **P14-05, подтверждённая граница источника:** service принимает только новые onNotificationPosted выбранного пакета своего Android-профиля при настройке и доступе; истории/банковского inbox нет. onListenerConnected обновляет статус, но не догружает прошлые события. Это надо явно различать с parser review. Отсутствующий системный event исходящего Kaspi из APP-009 расширением словаря не восстановить. APP-010 NO-GO и его границы остаются.
- **P14-06, ограничение идентичности, которое требуется сохранить:** SourceTokens строит HMAC revision в том числе из текста; изменение выбора полей может изменить revision одного уведомления. LedgerStore повторный sourceKey с другой revision без strong reference оставляет на проверке; одинаковая сумма/дата — лишь слабое совпадение. Нельзя отключать эти меры, чтобы повысить долю auto.

### Backend-engineer: извлечение и интерпретация, отдельный владелец

Предлагаемое владение только `BankNotificationService.java`, `core/BankMessageParser.java`, новым `NotificationText.java` при необходимости и новыми узкими тестами этих модулей. Общий `ParseSupport.java` и существующий `ParserTest.java` менять лишь после явного назначения chief, поскольку их использует receipt-путь.

1. Выделить ограниченное извлечение notification fields в тестируемый модуль, сохранив allowlist-before-extras и лимит 65536. Не складывать безусловно title/text/bigText/textLines: это создаёт дубли сумм или объединяет разные операции. Одинаковые полные строки/представления можно убрать; одинаковые денежные значения разных строк не являются доказательством дубликата. Если альтернативные представления противоречат друг другу или textLines содержит несколько операций, сохранить разбор для review.
2. Добавить точные bank-only валютные алиасы KZT, затем направления для явных «вам/получено/зачислено» и «вы/отправлено/списано»; переносить известные сумму/валюту/дату в review вместо пустой формы. Не приписывать направление без достаточного текста, не выводить дату из postTime при отключённом согласии, не выводить валюту из основной настройки.
3. По обезличенным реальным примерам и согласованному контракту — отдельные ограниченные шаблоны завершённой операции: одна сумма операции, отдельно помеченный остаток, отрицательные/плановые/отклонённые статусы имеют приоритет. Generic fallback остаётся. Переводы между своими счетами, кредит/долг/возврат, несколько направлений/операций требуют review. Включение автоматического учёта P2P требует явного правила продукта и доказанных шаблонов; удалить общий guard для всех переводов нельзя.
4. Составить синтетические проверки извлечения и направления; не объявлять их проверенным банковским корпусом. Возвратить точные команды/результаты и контракт data-engineer.

### Data-engineer: идентичность и отсутствие двойного учёта, отдельный владелец

Первый этап — read-only SourceTokens/LedgerStore/IngestSource и новый `team/reports/APP-014-data-review.md`; при необходимости отдельные новые tests. Изменения `SourceTokens.java`, `storage/LedgerStore.java` или схемы — только после отдельного ownership chief. Предпочтение: без миграции и без изменения денежной модели.

1. Проверить новую канонизацию notification text при одинаковом sourceKey/postTime: точный повтор, свернутое/развёрнутое представление, обновление содержимого, remove+repost, capture gap и перезапуск.
2. Проверить, что пересканированный/обновлённый источник и банковское уведомление не дают доказанно тот же платёж дважды автоматически; слабое совпадение суммы/даты не склеивает две реальные равные покупки. Без доверенного transaction/account reference не изобретать strong identity.
3. Сохранить tombstones/ignore и атомарность; новый parser не перепроводит существующие кандидаты сам по себе. Проверить, что смена парсера не повторно оживляет удалённое/отклонённое событие.
4. Деньги остаются точными целыми минимальными единицами по Money.scale; KZT имеет две десятичные позиции, другие валюты изолированы. Округление распознанной суммы не применяется: недопустимая точность — review/ошибка. Дата операции из источника; разрешённый postTime переводится в выбранный часовой пояс.

## Минимальные критерии и meaningful проверки

- Новые формы тг/теңге/тенге дают те же точные поля, что KZT; неизвестная/конфликтующая валюта не заменяется настройкой.
- Явные завершённые входящий/исходящий текстовые формы заполняют правильное направление; «не переведено», «ожидает», отмена, подтверждающий код, свои счета и реклама не auto-post.
- Баланс, комиссия, лимит, номер карты и две операции не принимаются за единственную сумму. Неполное альтернативное представление не теряет более полное, конфликт не скрывается.
- Большой/неверный extras, summary, другой профиль/пакет, отзыв доступа и переполнение очереди сохраняют отказ/статус, а не молча создают расходы.
- Native storage проверки повтора/обновления/ignore и равных самостоятельных операций; существующий parser/OCR suite не регрессирует. Проверки настоящих Android extras выполняются независимым QA после реализации, не имитируются простым чтением Java.

После специалистов глава отдельно проверяет изменения и фактические результаты; далее независимые QA и суд по новой зафиксированной версии. Данный план не заменяет ни один из этих этапов.
