## Подтверждённые наблюдения по коду

- `NativeRuntime.processMedia` вызывает реальный OCR, parser и SQLite ingest; результат `ingestCandidate` игнорируется, job получает только `completed`. Из него нельзя понять, расход проведён, нужен разбор или найден повтор.
- `ReceiptParser` ищет сумму только в хвосте той же строки после итоговой метки. Отдельная строка суммы не подхватывается. Локальные обозначения `тг`/`теңге` не поддержаны. Несколько итоговых строк, в том числе одинаковых, дают `AMBIGUOUS_TOTAL` и пустую сумму. Это ограничения реализации, а не доказанная причина конкретного чека пользователя.
- Storage schema version=1. Категории создаются только вручную. На повторных открытиях нельзя безусловно заполнять отсутствующие категории: пользователь мог их удалить или переименовать.
- Exact replay уже идемпотентен, требуется сохранить tombstones/существующие категории/операции и conservative paid/duplicate gates.

Полные `eng+rus+kaz` BEST модели данным eng-only опытом ещё не проверены.

Chief предложил полный BEST eng/rus/kaz как основной проход и прежний FAST eng/rus/kaz как подтверждающий. Глава **утверждает этот ограниченный дизайн для реализации**, с условиями ниже; это не утверждение исправленной программы и не снятие P1:

- Ровно два full-image прохода, один последовательный OCR worker, один общий уже декодированный/ориентированный bitmap с прежними byte/pixel/downsample guards (не более8M decoded pixels по существующей логике). В production не переносить диагностический перебор PSM/масштабов/32crop попыток.
- Предпочтительно максимум один resident `TessBaseAPI`: после primary сохранить bounded transient результат, recycle/switch model set, выполнить verification. Это ограничивает одновременную native model память; два одновременно resident engines требуют отдельного обоснования/замера peakmemory, которого пока нет. Модели BEST больше, низкая память остаётся реальным failure path, не сигналом ослабить guard.
- Отдельные pinned official BEST/FAST assets, пути, hashes и licenses принадлежат root; никаких сетевых загрузок из приложения. Копирование/проверка моделей один раз вместо безусловной многократной перезаписи при каждом переключении. `ocr.ready` сохраняет правдивую связь с успешным actual initialization, повторная инициализация после trim не выдаёт фиктивный success.
- Автопроведение только если оба прохода имеют complete canonical `kind/amount/currency/date`, high, пустые reasons (включая completed-paid gate) и confidence>=80 **каждого**; поля должны совпасть точно. Amount/date/paid uncertainty или любой конфликт → needs_review, приоритет prefill — структурированные поля BEST. Никакого majority vote, арифметического усреднения или увеличения confidence.
- Primary failure означает job failure, а не выдуманную запись. Verification failure/empty/OOM при пригодном primary не разрешает auto: review с LOW_CONFIDENCE; при невозможности безопасно завершить — job failure. Все handles/bitmap освобождаются по finally, raw OCR не уходит в JS/state/log пользовательских данных. Pure consensus helper проверяется отдельно.
- Замерить actual initialization и два прохода на синтетических изображениях, отразить размер APK/моделей и runtime ограничения. Hard deadline не обещан: синхронный JNI вызов не становится прерываемым от одного UI timeout. Не добавлять небезопасное убийство потока.
- Final actual test обязан использовать полные BEST3+FAST3 production и исходный неизменённый PNG с expected amount754.32. Независимый QA вправе ожидать `needs_review` вместо прежнего `posted` по новому guard, сохраняя исходный input/font/amount/date и явно проверяя отсутствие неправильного auto794.32. Дополнительные matching images должны подтвердить, что автоматизация при agreement остаётся. Если production BEST3 снова неверен либо оба models одинаково неверны, P1 не объявлять закрытым.

План и лимиты направлены chief и `/root/improve_native` реальными сообщениями. Глава продукт/тестовые ожидания не менял. До новой реализации, её actual Android проверки и независимого QA общий backend результат остаётся **не принят**.
