# APP-010: security review ограниченной проверки Kaspi

Версия 1, 2026-11-03. Исполнитель: security-engineer; передано architecture-lead для независимой проверки. Область работы — документация, без изменений приложения и телефона.

## Вывод

**NO-GO для реализации и установки пробы, читающей содержимое окна, при имеющихся вводных.** Не установлен способ подтвердить допустимый итоговый чек и четыре разрешённых поля **до получения банковского содержимого**. Это недостаток доказанного ограничения доступа, а не установленная несовместимость Kaspi или доказательство того, что банк скрывает текст.

Пользователь разрешил только локальную проверку текста уже открытого итогового чека: сумма, валюта, дата, статус. Разрешение не включает другие экраны, баланс, историю, пароли, снимки экрана, фоновый опрос, открытие банка, нажатия, жесты, автоматическое проведение расходов или запись в денежный журнал. Общая цель «без ручных действий» эти границы не расширяет.

## Выполненное и доказательства

- Прочитаны `AGENTS.md`, `team/PROTOCOL.md`, полный профиль security-engineer, задачи APP-009 и APP-010. Ожидалось установить актуальную границу согласия; факт: разрешена только описанная проверка, реализация зависит от положительного предварительного review.
- Проверены официальные Android API reference по состоянию на дату review. Ожидалось найти документированный способ отличить итоговый чек до чтения его содержимого; факт: изученные API предоставляют окна, узлы и признаки, но не документированный банковский receipt-only допуск. Наличие метода не доказывает совместимость с установленной версией Kaspi.
- `getRootInActiveWindow()` получает корневой узел активного окна с возможностью чтения содержимого; активность определяется касанием/фокусом, включая другой логический дисплей. В API 33 параметр prefetch допускает `0`; это ограничивает предварительную выборку, но не превращает запрос корня в проверку типа чека. [Android: AccessibilityService](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService#getRootInActiveWindow(int)).
- `packageNames` задаёт фильтр пакетов для событий. Это не ограничение доступа конкретным экраном. `isAccessibilityTool` описывает помощь людям с инвалидностью; финансовая проба не должна выдавать себя за такой инструмент. [Android: AccessibilityServiceInfo](https://developer.android.com/reference/android/accessibilityservice/AccessibilityServiceInfo).
- Callback AccessibilityButton сообщает о нажатии кнопки, а не удостоверяет итоговый чек или неизменность окна. [Android: AccessibilityButtonCallback](https://developer.android.com/reference/android/accessibilityservice/AccessibilityButtonController.AccessibilityButtonCallback#onClicked(android.accessibilityservice.AccessibilityButtonController)).
- `AccessibilityNodeInfo` содержит текстовые и структурные свойства; ID ресурса требует `FLAG_REPORT_VIEW_IDS`, `uniqueId` может отсутствовать. `isPassword()` — признак пароля; `isAccessibilityDataSensitive()` доступен с API 34. Эти признаки не удостоверяют разрешённый экран. [Android: AccessibilityNodeInfo](https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo).
- Начиная с API 34 `ACCESSIBILITY_DATA_SENSITIVE_YES` ограничивает взаимодействие сервисами с `isAccessibilityTool=true`. Защиту следует уважать; ложная декларация и обходы запрещены. [Android: View](https://developer.android.com/reference/android/view/View#ACCESSIBILITY_DATA_SENSITIVE_YES).

Попытка дополнительно открыть исходник AOSP через web-инструмент не дала читаемого содержимого; вывод о точном составе Binder/Parcel на её основании не делается. Документация не предоставляет доказанной гарантии metadata-only запроса для произвольного банковского узла. Получить NodeInfo, затем не вызывать `getText()` — недостаточное доказательство, что финансовое содержимое не было получено ранее вместе с узлом. Это инженерная оценка границы доступа, а не утверждение, что каждый корень непременно содержит все поля экрана.

## Замечания

- **SEC10-01 / P1 / блокирует реализацию: нет допуска до чтения.** Сценарий: нажатие кнопки происходит на балансе либо между нажатием и запросом банк сменил экран. Пакет совпадает; поиск слов «перевод»/«успешно» по текстам уже читает запрещённый экран. Неизвестны стабильные признаки конкретного итогового чека и его разрешённых полей. Проверка: без финансового текста доказать отсутствие совпадения на балансе, истории, форме перевода, авторизации и модальных окнах. Доказательств сейчас нет.
- **SEC10-02 / P1 / блокирует предложенную metadata-only разведку узлов.** Сценарий: обход корня/детей для поиска ID возвращает узлы с текстом или агрегированным content description прежде, чем выбран разрешённый чек. Не доказана доставка только метаданных. `prefetch=0`, выключение кеша и запрет getter текста не доказывают нужную границу. Не проводить такую разведку на телефоне в рамках текущего согласия.
- **SEC10-03 / P1 / обязательный запрет обхода.** Сценарий: данные скрыты, сервис получает `null`/неполный результат либо нужное поле помечено sensitive/password. Нельзя включать `isAccessibilityTool=true`, делать снимок/OCR экрана, расширять обход, вызывать действия или искать другое окно. Факт скрытия Kaspi не проверялся; это условие остановки будущей допустимой пробы.
- **SEC10-04 / P2 / происхождение и гонка окна не доказаны.** Пакет и не редактируемое поле не различают чек, баланс и историю. Нет проверенного контракта версии приложения, окна/дисплея, текущего Android-пользователя/профиля и источника полей. Нажатие пользователя не даёт этих гарантий; `windowId` не является банковской аттестацией. При неопределённости — остановка, а не предположение о личном профиле или повторный обход.
- **SEC10-05 / P2 / локальность не разрешает лишнее хранение.** Сценарий: отладочный `event.toString()`, дамп дерева, logcat, crash-отчёт, файл или аналитика сохраняют банковские данные. Ни сырые события, ни содержимое узлов, ни персональные данные не должны попадать в логи/артефакты/сеть. Проба не должна касаться БД приложения. Это условия будущего решения, а не найденная утечка существующего приложения.

Приоритеты относятся к рискам предлагаемого способа проверки. Сервис не написан и реальный инцидент не заявляется.

## Минимальные условия возможного пересмотра

1. Полученный без чтения посторонних финансовых экранов проверяемый контракт: конкретная версия/подлинный источник Kaspi, уникальное состояние итогового чека, допустимое окно/дисплей/профиль, точный набор четырёх полей. Одних предполагаемых view ID или инструкции пользователю «открой чек» недостаточно. Наличие такого контракта у банка не установлено.
2. Доказанное ограничение выдачи банковского содержимого разрешёнными полями **до** его получения, включая агрегированные описания узлов, события, предвыборку и смену окна. Повторная проверка после чтения не устраняет уже случившееся расширение доступа.
3. Только после этих доказательств рассматривать одноразовую цепочку: выключено → явный запуск → предзапросный допуск → получение четырёх полей в памяти → локальный результат → выключено. Неудача, неизвестная версия/профиль/окно, смена состояния, скрытое/отсутствующее поле или невозможность проверить password/sensitive означают немедленную остановку без повторов и fallback.
4. Любое будущее расширение до постоянного наблюдения или автоматической записи требует отдельного задания и согласия. Одноразовая проверка не реализует желаемый нулевой ручной ввод и не разрешает его автоматически.

## Ограничения и следующее действие

Не выполнялись: чтение телефона/экрана/уведомлений Kaspi, ADB, приватных логов, снимков или дерева UI; проверка реального чека; сборка/установка APK; выдача разрешения; работа с финансовой БД; runtime-тесты. Проверка является анализом задания и официальной документации, не проверкой безопасности приложения.

Передать этот вывод главе. Если предзапросный receipt-only допуск нельзя доказать в согласованных границах, завершить APP-010 результатом «безопасная проверка недоступна при текущих вводных». Не просить включить широкий доступ «чтобы посмотреть, что вернётся» и не заменять отсутствующее доказательство более широким чтением.
