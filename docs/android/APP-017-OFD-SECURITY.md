## Замечания и минимальный backend guard

**OFDSEC-01 / P1 / блокирует автопроведение без исправления identity lifecycle.** `NativeRuntime.java:251–252` сейчас использует `receipt-fiscal-qr-v1`: source HMAC от host/ФП/РНМ, revision HMAC от того же locator и canonical amount/timestamp. V2 назначает новый namespace/full locator/financial revision, но не назначает совместимость со старой парой токенов. `LedgerStore.java:335–343` подавляет только exact source+revision; guard изменённой revision `:367–377` относится только к notification. Weak match `:430–438` зависит от текущих amount/date; auto-post допускается в `:412–417`.

Сценарий по коду: offline review → пользователь меняет сумму или дату и проводит расход → API того же исходного QR возвращает high с новыми токенами → exact replay не найден, weak match может отсутствовать → возможна вторая запись. Аналогично новый token не сохраняет прежнее ignored решение. Device/SQLite воспроизведение здесь не запускалось; отсутствие нужного guard подтверждено чтением ветвей, их runtime должен проверить QA.

**Минимальное исправление без общей миграции:** для online и offline результата одного validated QR сохранить существующую пару source/revision токенов `receipt-fiscal-qr-v1`. В совместной паре уже присутствуют host/ФП/РНМ/total/timestamp; она не обязана зависеть от API confidence/type/items/metadata. API-first high может использовать обычные storage gates; fallback-first повтор возвращает прежний review/ignored/posted/linked без нового ingest и без перезаписи ручных правок. Такой MVP безопасно оставляет fallback кандидата на ручной проверке даже после позднего API success.

Если требуется автоматическое обогащение pending fallback, нужен отдельный atomic storage путь: найти исходный QR anchor независимо от отредактированных полей, проверить состояние/expectedRevision, обновить тот же допустимый pending candidate и не создавать вторую observation/transaction. Posted/linked/ignored и пользовательские правки сохраняются; API conflict — review, не новая high операция. Новая provider identity допустима только с explicit alias/legacy-token lookup до любого insert/post. У существующего store такой переход не предполагается.

**OFDSEC-02 / P2 / обязательные decoder guards реализации.** HTTP200 и SALE2 сами по себе не заменяют полный контракт: required typed TICKET, explicit cancel/offline null, exact fiscal/rnm/total/calendar timestamp match, известные платежи и exact sum==total; только тогда expense/high через storage. Unknown/refund/void/missing/wrong type/QR conflict → review/error. Деньги читать исходным decimal lexeme, до BigDecimal отвергать exponent/лишние нули fractional part/sign/overflow; duplicate неоднозначных financial keys тоже отвергать. `.000` допустимо только как нулевая часть согласованного timestamp, offset/nonzero fractions не угадывать. Это критерии будущего parser, его ещё не проверяли.

**OFDSEC-03 / P2 / обязательная граница сети и приватности.** Native сам строит GET только HTTPS443 `consumer.oofd.kz` path `/api/consumer-proxy/api/tickets/get-by-url` с четырьмя validated полями; JS/raw QR не задают адрес. Без credentials/cookies/redirects/HTML/WebView, обычная TLS validation; connect5s/total10s/cancel/body close, compressed и decompressed≤256KiB, depth≤16, items≤500, item name≤512 UTF-8 bytes transient. Никаких raw response/query/URL-bearing exception в logs/errors/JS/SQLite. Поля payload/card/account/seller IDs/RRN игнорируются, не копируются в fixtures/APK. Код клиента ещё не проверен; формальное наличие требований не является проверкой их исполнения.

**OFDSEC-04 / P2 / stable revision.** `acceptedAt`, `kkmId`, transport/found metadata и порядок/raw JSON не участвуют в финансовой revision или identity. Товарные строки полезны только transient и не заменяют net total. Иное фото, metadata drift и повтор после restart не означают новую покупку. Fiscal locator не становится bank payment reference; POS/notification without shared trusted bank identity остаются possible-match review/link.

На synthetic данных: API-first replay; offline→success; offline→ignore→success; manual amount/date edit→success; post/link→replay; restart и metadata drift; QR/API mismatch и изменение financial result на том же anchor.
