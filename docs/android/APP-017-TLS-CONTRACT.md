# APP-017 TLS contract v1 — дополнение цепочки, не trust store

2026-11-04. Автор `/root/kaspi_compat_arch_lead/receipt_gate_architect`; отдельная проверка главы/security обязательна. Полные профиль/AGENTS/PROTOCOL/APP-017 и architecture/backend reports прочитаны. Владение: только этот новый документ и назначенный private `tls-architect-*` probe; прежний OFD contract v3/source не изменялись.

## Решение и доказанный дефект

Минимальная auxiliary-chain схема **технически работоспособна на JDK21 и условно допустима к реализации после security review**: известный промежуточный сертификат подаётся штатному validator как недоверенный chain element. Системные trust anchors не расширяются. Предпочтительное исправление на сервере — передавать полную цепочку; клиентское дополнение ограничено этим provider и проверенным missing-one-issuer случаем.
Root сообщает Android/production-client SSLHandshake до HTTP и JDK PKIX failure; synthetic tests это не исправляют. Мой live TLS-only probe независимо зафиксировал presented chain **ровно1 сертификат**, leaf SHA256 `6FE957F4C1E702065AB6A8772FF0A0CC954B0F542DAA43A2172096FED4138584`; original DEFAULT delegate отклонил его. Это фактическое доказательство неполной presented chain на исследованном пути, не предположение по одному PKIX.

## Происхождение и версия auxiliary certificate

Root read-only metadata `tls-public-chain.json`: обычная Windows validation=true, chain leaf→GoGetSSL RSA DV CA→USERTrust RSA; intermediate DER1499bytes. Мною независимо получен тот же сертификат через HTTPS200 по [официальному каталогу GoGetSSL](https://www.gogetssl.com/wiki/intermediate-certificates/gogetssl-intermediate-root-certificates/), Legacy DV RSA [CRT](https://gogetssl-cdn.s3.eu-central-1.amazonaws.com/wiki/gogetssl-rsa-dv-ca.crt).
DER SHA256 **`43CAC31EF8E8BA1B4B16B8206E4C0A26C5BADB2FC3AA09E90170E41B66C2FD64`** совпал с independently DEFAULT-Windows-validated intermediate. Это asset-version identifier, не новый trust anchor и не leaf pin.
Subject `CN=GoGetSSL RSA DV CA,O=GoGetSSL,L=Riga,C=LV`; issuer USERTrust RSA Certification Authority; BasicConstraints CA=true/pathLen0, keyCertSign=true. Validity UTC `2018-09-06T00:00:00Z`–**`2028-09-05T23:59:59Z`**. Наивное «до06.09.2028» не использовать для runtime проверки срока.
Leaf AIA указывает `http://crt.usertrust.com/GoGetSSLRSADVCA.crt`; проба его HTTPS варианта завершилась HttpRequestException. Ни HTTP AIA download, ни доверие произвольному AIA не нужны: primary HTTPS catalogue bytes уже сверены. Production не скачивает CA/AIA и не принимает server-supplied certificate как автоматически доверенный.

## Нормативный алгоритм wrapper

1. Только отдельный OfdReceiptClient/его per-instance SSLContext и fixed `consumer.oofd.kz:443`. Создать исходный trust manager из DEFAULT TrustManagerFactory с `init((KeyStore)null)`, сохраняя platform trust/NSC policy. Не создавать свой trust-store, не импортировать intermediate/root/userCA, не заменять NSC и глобальные TLS defaults.
2. Требовать исходный `X509ExtendedTrustManager`; если platform type не поддержан — fail closed/обычный default failure, не переходить к упрощённому custom validator. Первый вызов всегда **original delegate с original chain, authType и тем же Socket/SSLEngine context**. При успехе ничего не дополнять.
3. После CertificateException разрешена ровно одна попытка дополнения, только при известном missing-one-issuer subset: исходная chain.length==1, auxiliary exact DER hash/CA/keyCertSign/validity корректны, leaf issuer==auxiliary subject и `leaf.verify(auxiliary.publicKey)` проходит. Контекст соединения обязан относиться к fixed provider. Не менять leaf, authType, алгоритмы, дату проверки, SSLParameters, SNI, hostname или входной массив.
4. Создать новый массив `[originalLeaf, knownIntermediate]`; **не помечать intermediate доверенным**. Повторить тот же original DEFAULT checkServerTrusted overload с теми же параметрами контекста. Только его успешный результат допускает соединение. Signature precheck/совпадение SHA/Windows success не заменяют DEFAULT PKIX validation и доступность системного root.
5. Socket и SSLEngine overloads делегировать соответствующим extended overloads; client-check overloads и getAcceptedIssuers — без расширения. Двухаргументный server overload может только выполнить original двухаргументную проверку; **не использовать его как repair fallback**, теряющий host/algorithm/NSC context. При отсутствии необходимого handshake/host context — исходная ошибка. Android host-aware/per-domain policy должна сохраниться, без reflection fallback на менее строгий API.
6. HttpsURLConnection сохраняет default HostnameVerifier; endpoint identification HTTPS и SNI сохраняют назначенный host. Никаких TrustAll, `return true`, custom root acceptance, hostname override, global socket factory, permissive catch или `CertificateException`→success. Если повторная DEFAULT validation не проходит, либо guard/asset/issuer/context неизвестен — safe TLS error, без альтернативного запроса/HTTP downgrade.

## Первичные API и фактическая проба

[JDK21 X509ExtendedTrustManager](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/javax/net/ssl/X509ExtendedTrustManager.html) связывает проверку chain с Socket/SSLEngine SSL parameters и endpoint/algorithm constraints. [Android X509TrustManagerExtensions](https://developer.android.com/reference/kotlin/android/net/http/X509TrustManagerExtensions) документирует host context. По [Android RootTrustManager source](https://android.googlesource.com/platform/frameworks/base/+/0f5d386/core/java/android/security/net/config/RootTrustManager.java) domain-specific trust выбирается через host-aware context; DEFAULT policy нельзя заменять plain root-list check. Это API обоснование, не доказательство работы wrapper на конкретном Android.
Запуск собственного `tls-architect-Probe.java` через JDK из root toolchain: **exit0**, DEFAULT `sun.security.ssl.X509TrustManagerImpl`, accepted roots118. Три публичных TLS handshakes, никаких HTTP bytes/QR/чековых запросов: (а) original chain/default reject ValidatorException→SSLHandshakeException; (б) та же chain + известный aux→тот же DEFAULT Socket-context accepted, TLSv1.2; (в) negative peer+SNI `wrong.invalid`→completed DEFAULT CertificateException с hostname rejection и SSLHandshakeException. Во всех случаях сервер показал тот же единственный leaf fingerprint.
Первая negative проба ошибочно оставляла matching SNI consumer и не создавала нужного mismatch; она не считается отрицательным доказательством. После исправления peer и SNI согласованно неверны, финальная проба выше прошла. Production SNI/hostname менять не разрешено.
Исследовательский wrapper сохраняет все extended overloads; live пройден Socket overload, engine/client paths runtime не проверялись. Chain остаётся без custom anchors; публичный intermediate используется только как вход DEFAULT validator. Локальные files root TLS certificate/metadata не менялись.

## Приёмка и открытое ограничение

Перед закрытием LIVE01/P1: независимый security review реализации/asset SHA; DEFAULT Android extended delegate и host policy подтверждены фактически; public TLS-only repair проходит на целевом Android; затем разрешённый normal production-client path без fake transport проходит. До этого **Android live исправление не доказано**, прежний P1 остаётся открытым.
Обязательные negatives будущей реализации: wrong host/SNI, expired leaf/aux, self-signed/untrusted root, substituted aux bytes, issuer mismatch, invalid signature, unknown/multiple/malformed chain, disabled/missing root, context absent/nonextended delegate. Всё должно оставаться reject; first-pass complete valid chain должна проходить без repair. При обновлении/истечении auxiliary сертификата нужен заново проверенный asset; никаких silent download/replacement.
Прежние fixed HTTPS path, no redirects/cookies/scripts, deadlines/body limits, no raw URLs/logging и финансовые guards не меняются. В этой подзадаче исходники/SSL store/телефон/банк/ledger не изменялись, Android/JVM product tests и чековые HTTP не запускались. Следующее действие: глава+security проверяют этот конкретный contract/probe, затем backend реализует отдельно и QA доказывает затронутые runtime критерии.
