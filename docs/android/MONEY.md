## Валюта, типы и хранение

- При первом запуске пользователь явно выбирает primaryCurrency и ZoneId; KZT или валюта системной локали не подставляются молча.
- Каталог — известные runtime `java.util.Currency.getAvailableCurrencies()` с `getDefaultFractionDigits()` в диапазоне 0..6 включительно. Неизвестный код, scale=-1 или вне диапазона недопустимы; 6 — технический предел APP-005, не финансовое правило.
- Код валюты — ISO-код из каталога. Native получает scale из Currency и сверяет переданный scale; записанный scale сохраняется вместе с суммой. Несовпадение — ошибка, без пересчёта существующих записей.
- MoneyDTO / поля операции: `{amount:string,currency:string,scale:int}`; amount строго положителен, знак задаёт wire-поле `kind=income|expense`; дата операции — wire-поле `date`, как в CONTRACT.md.
- Canonical amount: ASCII-цифры, целая часть `0|[1-9][0-9]*`; при scale>0 точка и ровно scale цифр, при scale=0 только целая часть. Нет плюса, минуса, экспоненты, группировки и ведущих нулей.
- Ввод одной операции ограничен 24 цифрами целой части после разрешённой нормализации; минимум `10^(-scale)`, максимум `10^24-10^(-scale)`. Это техническая защита ввода, не лимит состояния/оборота пользователя.
- Java: `minor = new BigDecimal(amount).setScale(scale, UNNECESSARY).unscaledValue()`, тип `BigInteger`; единица minor = `10^(-scale)` единицы валюты. Перед этим обязательна лексическая проверка ниже.
- SQLite хранит amount как TEXT, currency как TEXT, scale как INTEGER; bridge JSON передаёт amount строкой. Запрещены REAL, float/double, JavaScript Number/parseFloat и SQL SUM/CAST числовых сумм.
- Сложение/вычитание выполняются в BigInteger minor, без MathContext с ограниченной точностью, деления, округления или отсечения. Валюта и scale операндов должны совпадать.
- Агрегаты не ограничены 24 цифрами: результат длиннее сохраняется/передаётся/показывается полностью. При ресурсной ошибке вычисление завершается явной ошибкой, без частичного итога.
- Вывод строится из точных строк/minor, показывает валюту и все scale знаков; группировка и запятая допустимы только как представление. Обратное чтение форматированного вывода не заменяет исходный amount.

## Ручной ввод и нормализация источников

- Ручное поле явно задаёт точку или запятую как десятичный разделитель; группировка не поддерживается. Для scale=s>0 шаблон `(?:0|[1-9][0-9]{0,23})(?:[.,][0-9]{1,s})?`; для s=0 — только `(?:0|[1-9][0-9]{0,23})`.
- Любые пробелы, знаки +/- (включая отрицательный ноль), ведущие нули, оба разделителя, повторные разделители, пустая дробь, экспонента, NaN/Infinity, пустое значение и нулевая сумма отклоняются с сохранением ввода.
- После проверки заменить десятичную запятую точкой и дополнить недостающую дробную часть нулями справа: scale=2, `1,2` → `1.20`, `1` → `1.00`; scale=0, `1` → `1`.
- Число дробных цифр проверяется ДО BigDecimal; любое превышение scale отклоняется, включая `1.200` при scale=2 и `1.0` при scale=0. UNNECESSARY один не защищает от лишних нулей; stripTrailingZeros не применяется.
- Raw notification/OCR — только transient; в persistence и JS идут структурированный нормализованный кандидат, безопасные provenance и reasons, без raw текста/изображения/URI. Raw не попадает в JS/logs; private temporary media очищается после обработки/cancel и максимум через 24ч, с startup cleanup; исходное фото пользователя не удаляется. Нормализация требует однозначных суммы, валюты, завершённого вида и даты; ошибка не создаёт ноль/операцию.
- Пробельная группировка источника допускается только по полному шаблону: первая группа 1..3 цифры с ненулевой первой, затем группы ровно по 3 цифры, один вид разделителя U+0020/U+00A0/U+202F, необязательная десятичная часть. Например `1 234,50` → `1234.50` при scale=2; `12 34,50` → needs_review.
- Пунктуационная группировка разрешается только однозначным проверенным шаблоном конкретного источника. Общий fallback `1,234` и `1.234` → needs_review: это может быть дробь или тысяча; не выбирать по локали/scale. Ручной ввод следует явно объявленным правилам поля выше.
- После нормализации источника действуют те же ограничения цифр, точности, положительности и canonical; `1,2` → `1.20` при scale=2. Неоднозначные символы валюты, отсутствующая/неподдержанная валюта → needs_review, primaryCurrency её не заменяет.
- Источник с pending/cancelled/refund/transfer, неизвестным или противоречивым направлением → needs_review до явного решения пользователя. Сумма со знаком сама по себе не доказывает income/expense; автоматический модуль сохраняет только однозначно завершённую операцию.

## Дата и период

- `date` — настоящая ISO LocalDate `YYYY-MM-DD` (четырёхзначный год 0001..9999), строгая календарная проверка через LocalDate; `2026-02-29` недопустима. Время не встраивается в эту строку.
- Месяц `YYYY-MM`: включаются `date` в `[первый день месяца, первый день следующего месяца)`. Для 9999-12 верхняя граница вычисляется LocalDate следующего года, не сохраняется как `date` операции.
- Вручную выбранная дата не сдвигается через UTC. Настроенный валидный ZoneId определяет «сегодня» и преобразование timestamp; изменение зоны не пересчитывает сохранённые `date`.
- Для уведомления предпочтительна явная дата операции банка. Если она отсутствует, только при выбранной пользователем политике `POST_TIME_IN_ZONE` и известной зоне: `Instant.ofEpochMilli(postTime).atZone(zoneId).toLocalDate()`; provenance даты сохраняется.
- Нет явной даты и разрешённого fallback, дата неоднозначна/повреждена или ZoneId неизвестен → needs_review. `capturedAt` — момент получения/OCR, не подставляемая дата операции. Для чека без даты требуется разбор/выбор даты.

## Итоги, категории и повторная обработка

- В итогах только сохранённые подтверждённые операции (`posted`), не черновики/needs_review. Для одного месяца m, валюты c и scale s: `income=Σ minor(kind=income)`, `expense=Σ minor(kind=expense)`, `net=income-expense`.
- Пустые суммы = точный ноль; income/expense ≥0, net может быть отрицательным. Сводка использует canonical строки с точным scale; ноль/отрицательный net допустимы в агрегате, но не проходят положительный валидатор новой операции.
- Разные валюты/scale не складываются, не конвертируются и не сравниваются как одна денежная величина; сводки выдаются отдельно по выбранным month+currency. net — поток за период, не банковский баланс.
- Расход с categoryId=null входит в полный expense и отдельную группу «Без категории». Сумма всех категорий, включая null, равна expense; разрез не прибавляется к общему итогу повторно.
- Назначение/смена/удаление категории меняет только разрез: стабильный ID операции, amount, currency, scale, дата и полный итог сохраняются. Удаление категории переводит её записи в null, не удаляет расходы.
- Редактирование сохраняет ID операции и атомарно пересчитывает затронутые месяцы/валюты; смена даты октябрь→ноябрь переносит одну запись, не копирует её. Ошибка валидации сохраняет прежнюю версию целиком.
- Source использует wire-поля `eventId`, `sourceKeyToken`, `revisionToken` из CONTRACT.md. Exact revisionToken идемпотентен после restart/ручной правки: без новой записи и перезаписи. Новый payload/postTime/revisionToken — отдельное наблюдение, не вечное подавление по eventId/sourceKeyToken; отсутствие безопасной идентичности → review.
- Надёжный trusted paymentRefToken в одинаковом provider/account/reference namespace и непротиворечивые поля → `linked` к существующему ID, без новой суммы и перезаписи. Receipt fiscal ID не bank identity; сумма/время/фискальный ID либо иные слабые признаки дают только possibleMatch и `needs_review`, без второго расхода до manual link или явного `confirmDistinct`. Противоречия сильной identity тоже требуют review; контракт связей — CONTRACT.md.
- Налоги, ставки, FX, проценты, долг, цель и финансовая обработка переводов/возвратов в эту версию не входят; неизвестное не угадывается как доход/расход.

## Эталонные примеры для независимого QA

- scale=2: `0.01` → minor=1; `0.10+0.20` → minor=30 → `0.30`; income `1.00`, expense `1.20` → net `-0.20`.
- scale=2: `0`, `-1`, `+1`, `01.00`, `1e2`, `1 000`, `1.200`, `1.`, `NaN` → ошибка; никакой записи. scale=0: `1` допустимо, `1.0` недопустимо.
- scale=2: две операции по `999999999999999999999999.99` → `1999999999999999999999999.98`; отдельный ввод с 25 целыми цифрами отвергается, этот агрегат не обрезается.
- Расходы `1.20` с null и `2.30` с категорией → expense `3.50`; назначить/удалить категорию первой записи → expense по-прежнему `3.50`, две записи с теми же ID.
- Месяц 2026-10 включает 2026-10-01 и 2026-10-31, исключает 2026-11-01. Явная банковская дата 2026-10-31 при ноябрьском capturedAt остаётся в октябре.
- Повтор exact revisionToken → одна операция; новый revisionToken → отдельное наблюдение. Чек+push с надёжной общей payment identity → linked к одному ID; лишь сумма+время → needs_review до link/confirmDistinct, без удвоенного expense. needs_review не увеличивает income/expense до разрешения.

## Первичные источники и граница доказательств

- [Java Currency](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Currency.html#getDefaultFractionDigits()) — код/дробность валюты, включая неопределённую -1; проверено через web 2026-11-02. Каталог устройства проверяется при реализации отдельно.
- [Java BigDecimal.setScale](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/math/BigDecimal.html#setScale(int,java.math.RoundingMode)) — UNNECESSARY требует ошибки при необходимом округлении; точное удаление нулей допустимо, поэтому нужен лексический guard.
- [Java BigInteger](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/math/BigInteger.html) — арифметика целых произвольной точности в пределах ресурсов runtime; документация проверена через web. Тесты APK/Java/SQLite/UI здесь не выполнялись; глава, QA и суд принимают реализацию отдельно.
