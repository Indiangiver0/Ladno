# APP-010: предварительный контракт ограниченной проверки Kaspi

2026-11-03, Asia/Qyzylorda. Исполнитель `/root/kaspi_compat_arch_lead/receipt_gate_architect`, system-architect; проверяющий — architecture-lead. Прочитаны профиль, AGENTS.md, PROTOCOL.md и карточки APP-009/010. Это исследование документации, не проверка банковского приложения.

## Решение до реализации

**NO-GO для реализации читающего прототипа при имеющихся сведениях.** Подтверждённого признака, позволяющего до получения банковского содержимого отличить только итоговый чек Kaspi, сейчас нет. Неизвестны отдельный receipt-only Activity/window, проверенные resource IDs четырёх полей и их связь с версией Kaspi. Это недостаток необходимых сведений, а не доказательство, что Kaspi скрывает текст или что совместимость невозможна вообще.

Узкое согласие пользователя покрывает только уже открытый итоговый чек: сумму, валюту, дату и статус локально. Оно не разрешает читать остальные экраны, баланс, историю, пароли, просматривать их для поиска чека или автоматически проводить операцию. Разрешение Android на Accessibility технически шире этого согласия; последнее нельзя заменить стандартным системным переключателем.

## Что подтверждают публичные Android API

- `getRootInActiveWindow()` возвращает корень текущего активного окна, определяемого касанием/фокусом; окно может относиться к любому логическому дисплею. Возвращаемое значение может отсутствовать. Это не API выбора банковского чека. Требуется capability получения window content. [AccessibilityService](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService#getRootInActiveWindow())
- Window ID идентифицирует окно, а не финансовый смысл страницы. Title берётся из заданного приложением заголовка и может отсутствовать. Ни один из этих фактов не является публичным контрактом итогового чека Kaspi. Последнее — вывод этого исследования. [AccessibilityWindowInfo](https://developer.android.com/reference/android/view/accessibility/AccessibilityWindowInfo#getTitle())
- Resource ID можно получить при соответствующем `FLAG_REPORT_VIEW_IDS`; наличие метода не устанавливает реальные идентификаторы Kaspi. Node API также поддерживает предварительную загрузку связанных узлов, а password и sensitive — свойства узла (`isAccessibilityDataSensitive` с API34). Публичная документация не обещает отдельный запрос «только метаданные без содержимого» для классификации произвольной банковской страницы. Поэтому обход `AccessibilityNodeInfo` с отказом от `getText()` сам по себе не доказывает границу до получения содержимого. [AccessibilityNodeInfo](https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo)
- `packageNames` задаёт интересующие сервис пакеты; оно не классифицирует страницы внутри одного приложения. [AccessibilityServiceInfo](https://developer.android.com/reference/android/accessibilityservice/AccessibilityServiceInfo#packageNames)
- Callback accessibility button подтверждает нажатие системной кнопки, а не тип находящегося под ней экрана. Он может служить одноразовым пользовательским запуском будущей пробы, но не заменяет receipt gate. [AccessibilityButtonCallback](https://developer.android.com/reference/android/accessibilityservice/AccessibilityButtonController.AccessibilityButtonCallback#onClicked(android.accessibilityservice.AccessibilityButtonController))

## Обязательная последовательность для возможной будущей пробы

1. До установки/включения читающего сервиса должен существовать независимо проверенный, версионированный контракт именно receipt-only источника Kaspi. Он должен связывать доверенную identity пакета, допустимый профиль пользователя, окно/состояние и ровно четыре разрешённых поля. Предположения по похожему имени Activity или наличию слова `amount` в ID недостаточны. Обновление Kaspi, неизвестная версия или отсутствующее доказательство снимает допуск.
2. Одноразовый ручной запуск допустим только для проверки при уже открытом чеке. Он не превращается в периодический опрос, listener всех страниц или автоматическое открытие банка. Смена окна/экрана/профиля, неоднозначность active window, скрытое/защищённое/парольное содержимое либо потеря доступа завершает пробу без чтения полей. Нельзя доказывать, что это чек, предварительно прочитав произвольный `event.text`, title, content description, node text или результаты `findAccessibilityNodeInfosByText`.
3. После такого доказанного допуска — только ограниченное получение разрешённых полей через проверенные селекторы/контракт. Получение соседних узлов и prefetch не должно расширять фактический scope. Если этого нельзя обеспечить публичным API, ветка остаётся NO-GO; неизвестные узлы не исследуются «для обучения» на телефоне.
4. Только transient обработка четырёх значений. Результат совместимости может содержать наличие/доступность полей и безопасный код причины; raw дерево, значения, URI, screenshots, names/accounts не пишутся в логи/файлы и не отправляются наружу. Никаких вызовов ledger/import, финансовых изменений или идентификации операции для будущего автопроведения. Сервис не объявляется accessibility tool, которым не является, и не использует gestures/actions/screenshot capabilities.
5. Если gate или поля недоступны, результат — `UNSUPPORTED_OR_UNVERIFIED_SCOPE`; при обнаруженной платформенной защите — `CONTENT_UNAVAILABLE`. Не переходить к скриншотам, иной автоматизации, расширенному доступу, обходам или перезапуску банка.

## Минимум будущей проверки и текущее ограничение

Если отдельный receipt contract будет получен допустимым способом, независимый QA должен сначала на синтетическом адаптере доказать ноль обращений к содержимому для wrong package/profile/window/version, отсутствующего consent token, изменения страницы в том же окне, password/sensitive/hidden/null и ошибок. Положительный кейс читает только четыре разрешённых поля однократно и не пишет ledger/raw данные. Все геттеры/получения узлов, способные вернуть содержимое, входят в счётчик; проверять лишь отсутствие `getText()` недостаточно. Затем нужна отдельная проверка головы отдела и суда перед выдачей APK.

Ни один такой тест, сервис или APK сейчас не создан и не запускался. Телефон, Kaspi UI, ADB, банковские данные и старые 402 frozen файла не читались и не менялись этим исполнителем. Единственное изменение — этот новый документ. Следующий шаг — независимая проверка главы и сопоставление с выводом security-engineer; не начинать реализацию из предположения о доступности Accessibility.
