# APP-013 QR security review v1

2026-11-04, Asia/Qyzylorda. Исполнитель: security-engineer, передано architecture-lead; собственная приёмка не заявляется. Проверенная версия `APP-013-QR-CONTRACT.md`: SHA256 `20982166ACE1D7A6BEBF89719837225E0B301B0650DD58E617934687813B5E28`.

## Вывод

**Блокирующих замечаний к началу реализации локального MVP нет.** Известный фискальный QR заполняет точные KZT сумму/дату в кандидате `needs_review`, `kind=null`; пользователь подтверждает направление и запись. Это полезное заполнение чека без ожидания неподтверждённого API. Проверка реализации, QA и приёмка ещё впереди.

**Сетевой adapter остаётся выключенным.** Публичная форма reKassa и JSON ошибки пустого запроса подтверждают наличие consumer-интерфейса, но не успешную схему, стабильность стороннего API, тип операции или оплату. Отсутствие этих доказательств не блокирует локальное заполнение. Банковские экраны, accessibility, история и автоматический импорт переводов в этот контракт не входят.

## Проверено: ожидание и факт

- Целиком прочитаны `AGENTS.md`, `team/PROTOCOL.md`, профиль security-engineer и APP-013; затем конкретный контракт и MONEY.md. Ожидание: разрешённая QR-задача отделена от банковского чтения; факт: контракт сохраняет это разделение, сырой QR остаётся в native transient.
- Проверена версия контракта командой `Get-FileHash -LiteralPath 'docs/android/APP-013-QR-CONTRACT.md' -Algorithm SHA256`; факт — указанный выше SHA. Оценивался документ, исходники не менялись и runtime-проверки приложения не запускались.
- Ожидание: произвольный QR не создаёт загрузку URL. Факт в контракте: только exact `consumer.oofd.kz` + `/` и `ofd.rekassa.kz` + `/t/`, без userinfo/портов/fragment/поддоменов; ровно четыре однократных query-параметра `i/f/s/t`. HTTP разрешён только для локального legacy-разбора, HTTP-запрос запрещён. Native сам выбирает provider и строит будущий HTTPS URL; bridge не принимает адрес от JS.
- Ожидание: непроверенные данные не становятся денежной операцией. Факт: сумма без float/округления, scale2/KZT только известной KZ форме; строгая календарная дата без UTC-догадок; unknown type/paid/bank identity не выводятся из QR. Неизвестная валюта не заменяется primaryCurrency; нет пустого кандидата с guessed currency.
- Ожидание: конфликт и повтор не добавляют второй расход. Факт: до 16 QR/4096 UTF-8 bytes; превышение — ошибка; несколько/смешанные QR без безопасного выбора → `QR_MULTIPLE`; конфликт QR/OCR → review. HMAC по существующим purpose/namespace правилам, fiscal locator не bank payment reference, ручные правки и игнорирование сохраняются.
- Ожидание: потенциальная сеть не расширяет доверие к содержимому. Факт: константный HTTPS443 host/path, обычный TLS, без redirects/cookies/HTML/scripts/WebView; connect5s/total10s, 256KiB после распаковки, JSON depth16. Auth/CAPTCHA/429/неизвестная схема → ошибка без обхода. До положительного source-backed ответа и проверки схемы этот путь не включается.

## Замечания и условия проверки реализации

- **QRSEC-01 / P2 / уточнение, локальный MVP не блокирует.** Формулировка контракта о расширении «whitelist» QR reasons излишне конкретна: глава отдельно установил, что текущий `ImportCandidate.fromJson` проверяет формат `[A-Z][A-Z0-9_]{0,63}` и размер списка, а не enum. Безопасный путь v1 — существующие `UNKNOWN_KIND`, `LOW_CONFIDENCE`, `IDENTITY_UNCERTAIN`; новые ошибки возвращать через согласованный error transport и понятный UI. Не менять DTO наугад. Самостоятельный анализ реализации parser/UI в этом review не проводился.
- **QRSEC-02 / P2 / обязательная реализационная проверка URI.** Недоверенные query и URI требуют строгой лексической проверки до нормализации. Проверять raw path точным сравнением с разрешёнными формами, декодировать только query один раз, искать duplicate по декодированным ключам; не применять substring/endsWith trust или повторный decode. Ожидание для userinfo, похожего домена, `%26`, malformed `%`, backslash, encoded path и повторных ключей — отказ без сети/операции. Факт: основные границы описаны контрактом; конкретный parser ещё не написан и эти векторы не запускались. Это критерий реализации, а не найденная уязвимость продукта.
- **QRSEC-03 / P2 / граница сетевой готовности.** Точный positive response decoder и связь ответа с тем же locator/суммой/датой не доказаны. Поэтому включение adapter сейчас нарушило бы контракт. Факт: adapter в документе явно выключен. Не использовать guessed receipt ID, личный чек у неизвестного сервиса или merchant credentials в APK для получения доказательства.
- **QRSEC-04 / P2 / корректность фикстур.** Исторический официальный пример с `consumer.test-oofd.kz` и `s=0.0` должен отвергаться production classifier. Он не может считаться positive fixture v1. Положительный тест — явно synthetic URL разрешённой формы с положительной суммой и валидной датой, локально, без HTTP и без заявления о найденном реальном чеке. Глава подтвердил такое разделение.

QRSEC-01 и QRSEC-04 — уточнения передачи в разработку. QRSEC-02 — обязательная проверка написанного parser, QRSEC-03 закрыт для локального этапа выключенной сетью. Подтверждённых P0/P1 в документе не найдено; безопасность будущего кода этим не утверждается.

Уточнение главы для первой реализации: при наличии QR выполняется только QR-путь, OCR не запускается; при отсутствии QR сохраняется прежний OCR. Unknown/multiple QR дают ошибку без входящего. Это допустимое сужение контракта, устраняющее смешивание QR/OCR в v1. INTERNET и сетевой stub не добавляются. `kind=null` не объявляется обходом duplicate guard: глава отдельно проверил повторную проверку weak matches при ручном подтверждении вида.

## Первичные основания и пределы

Официальная документация Android требует разбирать URI и проверять scheme/host целиком; частичные строковые проверки создают ошибки доверия. [Unsafe URI loading](https://developer.android.com/privacy-and-security/risks/unsafe-uri-loading). Bridge доступен JavaScript-фреймам WebView, поэтому внешние страницы/чековые HTML не должны попадать в WebView с native bridge. [WebView native bridges](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges). Cleartext traffic следует явно запрещать для сетевых запросов. [Network security configuration](https://developer.android.com/privacy-and-security/security-config).

Публичные страницы [КГД: опубликованная маска QR](https://www.gov.kz/org/kgd/documents/details/59860?lang=kk), [ОФД: consumer endpoint](https://www.oofd.kz/faq/7), [reKassa `/4ek`](https://ofd.rekassa.kz/4ek) прочитаны без идентификаторов чеков. Историческая маска — основание узкого local parser, не утверждение актуального закона. Описание inline JS и двух пустых GET `/t/` получено из конкретного отчёта архитектора; этим специалистом положительный ответ ОФД не запрашивался и не проверялся. Реальные QR/чеки, банковские данные, секреты, телефон, ADB и приватные логи не использовались.

Следующее действие: глава независимо проверяет эту версию и передаёт local-only реализацию владельцам native/UI. До выдачи APK нужны meaningful parser/точность/duplicate проверки и независимый QA по разрешённым synthetic данным. После появления доказанной схемы consumer-ответа сетевой adapter рассматривается отдельно; расширять доступ к банковским экранам для этого не требуется.
