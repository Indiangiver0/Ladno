## Решение и конкретный MVP

**Можно реализовать сейчас:** добавить локальный QR decoder к существующему native capture камеры/галереи, распознать ограниченный известный формат KZ fiscal QR и заполнить сумму KZT и дату во «Входящих». Кандидат всегда `needs_review`, `kind=null`, `confidence=uncertain`: QR с суммой не доказывает продажу вместо возврата, факт оплаты и принадлежность расхода пользователю. Пользователь выбирает вид/категорию и подтверждает запись. Это автоматизация заполнения, не обещание автоматического проведения.

**Внешний путь частично подтверждён:** публичный официальный consumer frontend reKassa строит фиксированный GET `/t/` с `i/f/s/t`; пустой GET реально возвращает JSON ошибки. Успешная схема ответа, доступность товарных строк/типа/оплаты и стабильность для стороннего приложения ещё не проверены. Поэтому локальный MVP не зависит от сети; сетевой adapter до этих доказательств выключен и не выдаёт фиктивных результатов.

**Не подтверждено:** универсальный открытый API всех ОФД/Kaspi без договора/ключа; API банковской истории/доходов по QR. Наличие сайта проверки не устанавливает контракт машинного API. Фактический QR пользователя не получен, покрытие его чека пока неизвестно.

## Первичные источники и границы доказательств

- [Опубликованный КГД текст приказа №208, п.98.1–98.2](https://www.gov.kz/org/kgd/documents/details/59860?lang=kk): маска `Протокол://URL?i=ФП&f=РНМ&s=сумма тенге.тиын&t=датаTвремя`. Это источник известного формата; документ старый, актуальность юридического требования на 2026 год здесь не утверждается. Маска не содержит вид операции, позиции или статус оплаты.
- [Официальный SFD KKM API QIWI v1.0.1](https://arm.osfd.kz/qiwi_kkm_api_v1.html), раздел результата `REGISTER_TICKET`: опубликованный hex-пример декодируется в `http://consumer.test-oofd.kz?i=1196572871&f=678980123456&s=0.0&t=20200518T181817`. Это тестовый пример, не рабочий чек и не production endpoint. Интерфейс регистрации ККМ требует регистрации и ключевой пары; это не consumer retrieval API. Test-host в production registry не добавляется.
- [Официальный FAQ ОФД «Казахтелеком»](https://oofd.kz/faq/7) направляет покупателя на `https://consumer.oofd.kz`. [E-Kassa integration](https://oofd.kz/page/freekkm_integrator_page) описывает API кассы для её владельца, а не доступ к произвольным чекам покупателей.
- [Официальный COMRUN/reKassa portal](https://ofd.rekassa.kz/portal/) прямо сообщает о проверке без входа и ведёт на [публичную форму `/4ek`](https://ofd.rekassa.kz/4ek). Её полученный HTML/inline JS: `queryParams.append('i', formData.value['fiscalSign'])`, аналогично `f=rnm`, `s=amount`, `t=finalDateTime`; `finalDateTime` — `YYYYMMDDTHHMMSS`; затем `window.open(window.origin + '/t/?' + queryParams)`. Реальный GET `https://ofd.rekassa.kz/t/` без параметров: HTTP400, `application/json; charset=utf-8`, `{"error":"No params"}`. Это **frontend-derived consumer interface**, не опубликованный стабильный JSON API/SLA; успешный чек этим исследованием не запрашивался.
- [Kaspi Гид, обновлено 28.05.2026](https://guide.kaspi.kz/client/ru/app/fiscal_receipt_check/q18863) подтверждает проверку фискального чека через QR либо сумму/дату/время/РНМ/ФП. Он не документирует consumer JSON API или выгрузку личных переводов. [ТТК `/check_ticket`](https://ofd1.kz/check_ticket) показывает форму дата/РНМ/ФП и предупреждение о демоверсии; машинный adapter по этому факту не назначается.

## Границы модулей и классификация

Путь: `native media → local QR decode → strict classifier → optional verified provider adapter → canonical ImportCandidate → существующий storage/review`. QR raw и URL остаются transient native данными, не передаются WebView/JS, SQLite, аналитике или логам. Не загружать/исполнять QR как страницу. Native контролирует capture и provider registry; bridge не принимает URL/host/ключ/путь от JS. Существующие `scanCamera`/`scanGallery` payload `{}` можно сохранить; отдельная кнопка QR — согласуемое UI расширение, не новый URL transport.

Начальный offline registry — только точные host/path: `consumer.oofd.kz` + `/` (пустой путь нормализуется в `/`) и `ofd.rekassa.kz` + `/t/`. Для первого сочетание production-host из FAQ и исторической маски — совместимый **локальный** parser, не доказательство online response. Для второго путь и параметры подтверждены живым frontend. Не принимать поддомены/похожие суффиксы, `test-*`, userinfo, порты, fragment, скрытые управляющие символы или иной путь. `http` допускается лишь как локально разбираемый legacy текст для этих точных форм; HTTP запрос не выполняется. Bare URL и неизвестные варианты не угадываются.

Параметры ровно `i,f,s,t`, по одному каждого; порядок несущественен. Разбор URI и декодирование query — однократные, без повторного decode; неожиданное поле/duplicate/неверная encoding → неподдержанный формат. `i` трактуется как ФП, `f` как РНМ по маске и reKassa JS; техническая граница каждого — 1..32 ASCII цифры, строкой с сохранением нулей, не числом. Это защитный subset, не заявление официальной универсальной длины. Никаких каскадных догадок «поменять i/f местами».

Декодер работает только с выбранным снимком и под существующими image limits. Новый лимит QR payload — 4096 UTF-8 bytes, не более 16 decoded QR на изображение; превышение — явная ошибка, не усечение. Несколько различных fiscal QR → выбор пользователем в безопасном native UI либо `QR_MULTIPLE`; не брать первый/крупнейший. Один fiscal QR рядом с payment/unknown QR можно использовать только как явно выбранный fiscal результат; payment QR не означает оплаченный расход. Если безопасного выбора пока нет, MVP возвращает `QR_MULTIPLE`. Повтор одного и того же QR на фото сворачивается transient до одного observation.

## Деньги, дата, candidate и повторы

- `s`: только ASCII decimal `(0|[1-9][0-9]{0,23})(?:\.[0-9]{1,2})?`. Без знака/экспоненты/запятой/группировки; лишние дробные разряды, включая нули, отклоняются. Native `BigDecimal`/`BigInteger` → canonical string ровно scale2, без float/double/округления. Например `1234.5 → "1234.50"`, minor `123450`. Ноль не создаёт нулевой расход: `QR_AMOUNT_INVALID`. KZT/scale2 следуют только из подтверждённой KZ маски, не из primaryCurrency/локали. Неизвестный формат с похожим `s` этой привязки не получает.
- `t`: строго `yyyyMMdd'T'HHmmss`, реальные календарные дата/время, year0001..9999. `date` сохраняет локальную дату этого чека `YYYY-MM-DD`, `dateOrigin=source`; время без offset не становится выдуманным UTC instant. `capturedAt` остаётся временем наблюдения, не датой расхода. Не использовать дату/сумму из соседнего QR или другого чека.
- Local mapping: `kind=null`, нормализованные `amount/currency/date`, `dateOrigin=source`, безопасная фиксированная note, `paymentReference=null`, `confidence=uncertain`; reasons совместимые с действующим контрактом: `UNKNOWN_KIND`, `LOW_CONFIDENCE`, `IDENTITY_UNCERTAIN`. Дополнительные QR-specific reasons требуют согласованного расширения whitelist, а не самовольных строк в строгом DTO. `needs_review` — статус storage, не выдуманное поле ImportCandidate. Отсутствующая доказанная currency при nonnull amount нарушает действующий DTO: неизвестный QR не отправляется туда с guessed currency; остаётся ошибка/отдельный transient draft без создания пустого кандидата.
- `source.kind=receipt`, native UUID `eventId`, HMAC `sourceKeyToken/revisionToken` по существующим purpose/namespace правилам. Receipt fiscal locator не bank paymentReference. Для повторного QR допустим согласованный receipt-scoped HMAC точного validated provider locator и normalised payload; не raw URI и не глобальный hash. Это идентичность наблюдения QR, не доказанная банковская операция. Повтор не затирает ручные правки и игнорирование; конфликт повторного payload требует review. Сумма+время с уведомлением дают только possible match, не auto-link/второй расход.
- OCR можно сохранить как отдельный источник полей того же выбранного чека; QR/OCR расхождение требует review без молчаливой победы одного. Их совпадение не поднимает QR до high и не доказывает оплату/вид. Предыдущая возможность удаления/игнорирования входящего должна работать для QR кандидата так же, как для OCR.

## Внешний adapter и проверяемые ошибки

Первый возможный online adapter — **только** provider `rekassa-consumer-v1`: native заново строит `https://ofd.rekassa.kz/t/?i=…&f=…&s=…&t=…` из validated полей, никогда не fetch raw QR URL. До включения нужны source-backed успешный demo/own-authorized ответ, точный success/error decoder, проверка связности ответа с тем же locator/суммой/датой, доступности operation type/items/payment evidence, условия использования и независимая security/QA проверка. Ключи не требуются формой; отсутствие требования на форме не доказывает отсутствие будущей авторизации/лимитов. Для других интерфейсов условия/ключи получаются официально, не выдумываются и не вшиваются в APK.

Сетевые границы предлагаемой реализации: HTTPS443 с обычной проверкой TLS, exact host/path/method registry, redirects выключены, никаких scripts/WebView/HTML исполнения, cookies/банк-токенов; timeout connect5s/общий10s, response≤256KiB после декомпрессии, JSON depth≤16. Пределы — наши защитные решения, не лимиты ОФД. HTML/неожиданный Content-Type/схема, смена provider endpoint, auth/CAPTCHA/429/ошибка сервера → безопасная ошибка, без обхода и без произвольного fallback. Успешный JSON разбирается native в typed модель; его содержимое не рендерится. Требуется отдельное разрешение INTERNET только native networking; прежний запрет WebView network остаётся.

Пользователю: `QR_NOT_FOUND` — «QR не распознан, попробуй ближе и без бликов»; `QR_UNSUPPORTED` — «Этот QR пока не поддерживается»; `QR_MULTIPLE` — «На снимке несколько QR, оставь один фискальный чек»; invalid amount/date — «Не удалось надёжно разобрать сумму/дату»; offline/network/provider unavailable — «Данные из QR заполнены, проверка ОФД недоступна» только если локальные данные действительно получены. Без них — явная ошибка без пустого входящего. Ни одна ошибка не создаёт подтверждённую операцию.

Проверки будущей реализации: официальный тестовый пример локально; деньги `1`, `1.2`, `1.20`, ноль, 24/25 digits, `1.200`, overflow/invalid date; malicious host/userinfo/path/duplicates/encoded delimiters/redirects/oversize; payment и несколько QR; конфликт OCR; повторы после рестарта/игнорирования; source identity отдельно от bank identity. Positive local case обязан дать ровно KZT сумму/дату с unknown kind и review без ledger; offline scan не выполняет HTTP. Network positive проверяется только по разрешённому synthetic/demo или собственному чеку с согласованным scope.

## Выполненное и следующий шаг

Выполнены чтение первичных публичных страниц и frontend `/4ek`, два пустых GET `/t/` без идентификаторов (первый получил JSON ошибки, второй уточнил HTTP400 и Content-Type), разработка этого контракта. Не передавались личные QR/чеки, не выполнялись bank UI/accessibility/ADB, исходники/APK/402 frozen не менялись, тесты продукта не запускались. Первые shell HTTP чтения в sandbox завершились DNS ошибкой; разрешённые read-only запросы затем выполнены с escalation. Глава и security проверяют документ, затем могут назначить конкретную реализацию локального MVP; сетевой успешный decoder пока остаётся отдельной неподтверждённой зависимостью.
