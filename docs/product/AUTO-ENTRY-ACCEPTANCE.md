# APP-004 — условия приёмки ввода операций

Версия: acceptance-draft-v2, 02.11.2026, Asia/Qyzylorda. Авторский материал для product-lead; собственная приёмка не выполнена.
Основание: APP-004 и PERSONAL-MVP.md requirements-draft-v2 (R1–R5, U5): Android выбран пользователем, желаемый охват — «все банки». Push/SMS ещё не определён.
Область: спецификация следующего этапа; эти сценарии не подтверждают реализацию OCR, уведомлений или поддержку банков в local-prototype-v1. Прежние 46 файлов не изменяются.

## Подтверждённые функции и проектные решения

- R1: учёт доходов; R2: учёт расходов; R3: категории расходов; R4: скан чека с автоматическим занесением расхода; R5: чтение уведомлений с занесением дохода/расхода без обязательной категории и возможностью изменить её позже.
- Обязательная семантика R3–R5: отсутствие категории не блокирует автозапись по R5, категорию можно назначить/изменить позднее; полная ясная валидная операция по R4/R5 создаётся автоматически без подтверждения пользователем каждого события. Это подтверждённые требования, повторного продуктового согласования они не требуют.
- U5: Android выбран пользователем; «все банки» — требуемый охват, а не доказанная совместимость всех форматов. Возможное использование папой не задаёт общий бюджет или синхронизацию.
- AP1 (предложение, PERSONAL-MVP P1): ручное добавление и исправление полей операции как дополнительный способ ввода.
- AP2 (предложение, P2/P5): неполный или неоднозначный результат остаётся видимым кандидатом с причиной проверки; конкретный маршрут разбора требует согласования и не меняет обязательный ясный автопост R4/R5.
- AP3 (предложение представления R3/R5): отсутствие категории хранится как `category=null`, отображается явно и не заменяется скрытой категорией «прочее». Само отсутствие обязательной категории и её последующая смена уже заданы R3/R5.
- AP4 (предложение, P3): повтор одного события не создаёт вторую операцию; связь чека и уведомления определяется доказательствами, а сумма и близкое время сами по себе недостаточны.
- AP5 (предложение, P4/P5): видны происхождение, состояние и исправления; состав и срок хранения исходников согласуются с безопасностью.
- AP6 (предложение архитектуре): общий вход событий и расширяемые распознаватели; неизвестный формат виден как неподдержанный/требующий разбора, а не как успешная операция. Это не выбранный стек.
AP1–AP6 — проектные критерии для согласования. Условны только части сценариев, относящиеся к этим предложениям; обязательные R3–R5, включая автопост AC-03/AC-05, сохраняют силу. F1/F2 нужны для реализации и проверяемых входов, а не для новой санкции на автоматическое создание операции.

## Входы и независимые ожидания

- F1 — необходимый финансовый контракт: реальные валюты, представление и точность суммы, округление, знак/направление, дата операции и часовой пояс, период итогов; правила возвратов, переводов, комиссий, отмен и обновлений. Сейчас не утверждён.
- F2 — контракт распознавания: поддерживаемые источники/форматы и язык чека, обязательные поля, допустимое восстановление пропусков, признак достаточной уверенности, идентичность события/покупки. Числовой порог OCR и точность распознавания не заданы.
- D1 — только синтетический пример для проверки сценариев: KZT, 2 десятичных знака, сумма A=1 200,00, B=2 300,00; дата 02.11.2026, зона +05:00, окно проверки — этот день. Значения точные, округление примеров не требуется; это не выбор реальной валюты/периода приложения.
- D1-чек: итог A, внесено 2 000,00 KZT, сдача 800,00 KZT, налоговая строка 120,00 KZT; дата и валюта явно присутствуют. Эталон расхода — A, а не внесённое/сдача/налог.
- D1-события — обезличенные тестовые входы с заданными идентификаторами, направлением, валютой и датой; не реальные уведомления. Для приёмки QA получает отдельно размеченные исходники и ожидания от финансового отдела, не из результата реализации.

## Наблюдаемые сценарии: вход → действие → ожидаемое

- AC-01 (R1/R2, AP1): два ручных ввода D1, доход A и расход B → сохранить каждый → видны две операции с соответствующими типами, точными суммами, валютой и датой; отсутствие категории не блокирует расход. Проверка формы после утверждения AP1/F1.
- AC-02 (R3/R5; AP3 — представление): расход без назначенной категории → открыть, назначить категорию, затем сменить её → показана последняя категория, та же операция и неизменные сумма/валюта/дата; обязательного выбора при автозаписи не было. При согласовании AP3 исходное значение — `category=null`.
- AC-03 (R4, обязательный автопост): D1-чек, признанный полным и однозначным по F2 → сканировать → один расход A появляется автоматически; подтверждение каждой записи и ручной ввод суммы не требуются. Дополнительно предложенная видимость происхождения проверяется по AP5.
- AC-04 (R4; AP2 — только сомнения): тот же чек с итогом, внесённым, сдачей и налоговой строкой → распознать → расход A; остальные суммы не создают самостоятельных расходов и не подменяют итог. Если итог неоднозначен по F2, предлагается AC-06.
- AC-05 (R5, обязательный автопост; AP3 — представление): два полных ясных валидных D1-события, одно о доходе A, другое о расходе B → передать выбранным доступным каналом → автоматически появляются соответствующие две операции без назначенной категории; подтверждать каждую не требуется. При согласовании AP3 значение — `category=null`.
- AC-06 (R4/R5, AP2): размытый итог или две равновозможные суммы/направления → распознать → виден кандидат, причина и доступные сведения; обычная денежная операция и её влияние на итоги не создаются до разрешения неоднозначности.
- AC-07 (R4/R5, AP2): отдельные варианты без валюты, без даты, без суммы → обработать каждый → пропуск виден, значение не выдумано; если F1/F2 ещё не разрешают достоверное восстановление, кандидат не попадает в денежные итоги. Дату получения нельзя молча выдать за дату покупки.
- AC-08 (R4/R5, AP4): один полный валидный D1 source event доставлен дважды, затем обработка повторена → открыть учёт → ровно одна денежная операция A; повтор не меняет сумму/категорию исправленной записи и не теряет связь с источником.
- AC-09 (R2/R5, AP4): две доказанно разные покупки A с разными событиями близко по времени → обработать → две операции, общий расход 2 400,00 KZT в окне D1; совпадение суммы/времени не объединяет их.
- AC-10 (R2/R4/R5, AP4): чек A и банковское событие A доказанно относятся к одной покупке по F2 → обработать в обоих порядках → один расход A со связью обоих источников; второй источник не увеличивает итог.
- AC-11 (R2/R4/R5, AP4): расход A уже создан по чеку, новое сообщение A только похоже по сумме/времени → обработать → сообщение остаётся кандидатом с сомнительной связью, текущий итог A; после решения «одна покупка» итог A, после доказанного решения «разные» — 2 400,00 KZT. До решения кандидат не влияет на итог, статус виден.
- AC-12 (R5, AP2/AP4): обновление того же банковского события повторяет A, затем меняет сумму на B → обработать → повтор A не создаёт запись; изменение не добавляет независимую покупку и не перезаписывает пользовательскую правку молча. Применение B проверяется только по утверждённому правилу F1/F2; без него изменение требует разбора.
- AC-13 (R3/R5, AP1/AP5): автоматический расход A без категории → назначить категорию, затем исправить сумму на B → одна операция с B и выбранной категорией, происхождение/факт исправления различимы; исходное A не остаётся вторым расходом. Редактор суммы — предложение AP1, не буквальное R3.
- AC-14 (R1/R2/R5, F1): сообщение о возврате или внутреннем переводе → распознать → без выбранного финансового правила не появляется обычный доход/расход; событие видно для разбора. После утверждения F1 QA задаёт отдельные ожидания, включая влияние на итоги.
- AC-15 (U5/R5, AP6): синтетический неизвестный формат банка → передать через доступный выбранный канал → не теряется молча и не объявляется успешным доходом/расходом; новый распознаватель проверяется на размеченных входах и повторе AC-08. Это проверка расширяемости, не доказательство поддержки «всех банков».
- AC-16 (R1–R5, AP2/AP5): после смеси ясных, сомнительных и исправленных входов → открыть учёт → различимы добавленные операции и кандидаты; в итогах учитываются только денежные операции, каждый статус соответствует фактической обработке. Временные нормативы пока не заданы.

## Открытые вопросы и передача

- Q-A1: Android и охват известны; нужны push/SMS, целевые версии/устройства, список проверяемых форматов и обезличенные примеры. «Все банки» нельзя объявить проверенным по нескольким шаблонам; полнота охвата требует согласованного набора и границ доказательства.
- Q-A2: F1/F2 отсутствуют; финансовый отдел должен дать независимые денежные эталоны, архитектура — контракт идентичности/доставки, безопасность — допустимую обработку исходников. Критерии сумм/обновлений/возвратов нельзя закрыть выдуманным правилом.
- Q-A3: product-lead согласует AP1–AP6, восстановление пропущенных полей, видимость неподдержанного формата и поведение неоднозначной пары источников; QA затем проверяет выполнимость и достаточность AC-01–AC-16.
- Q-A4: перечень категорий, языки/качество чеков, реальные валюты, даты/периоды, хранение и возможный отдельный учёт папы остаются вопросами; семейная синхронизация не добавлена.

Readback и контроль структуры выполнены только для документа; проверки приложения, OCR, уведомлений, банков и независимый QA не выполнялись.
